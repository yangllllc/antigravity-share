## 二、修复批复错版
**修改目标**　重点检查 `governance.py`、`review_ui.py` 和 CLI。每份批复绑定 `run_id` 和用户实际看到的不可变提案版本，例如 `plan_hash`；计划同时绑定对应的抽取 manifest。在线审阅页、离线导出的 `decisions.json`、对话内批复使用同一校验。缺少版本信息的旧批复要求重新审阅。缺项保持待审，只有明确驳回才写负反馈。
**回归用例**
1. 同一 run 的 V1 为“双栏”，V2 改成“单栏”，两版均含 `OP-001`。分别经三个审阅入口提交 V1 批复。三者均应拒绝；主题、晋升规则、编译视图、账本、水位均保持提交前状态。
2. V2 正确批复成功一次。重复提交同一批复应返回原收据，业务状态只变更一次。另测错误 run、重复或未知 `op_id`、漏批，均不得被静默接受。
3. 将同一会话拆成两个批次。只审完一个批次时不能推进该会话水位。两个批次均已处理且明确零候选，允许推进水位。已有候选但批复缺项时，不能将其记成用户驳回。
**验收条件**　只有用户审过的版本能落盘；失败没有业务副作用；重复提交幂等；水位能区分“已审完且无候选”和“尚未审完”。保留原有 `base_hash` 漂移检查。
## 三、修复 revert 误删
**修改目标**　重点检查 `governance.py` 的收据生成和 `revert_item`。一次操作涉及的所有条目都记录前后状态，包括被 `supersedes` 改写的旧条目。撤回时在锁内先核对所有受影响条目的当前状态，再整体还原。历史收据缺少必要证据时，明确列出冲突并安全退出。
**回归用例**
1. A 为 active，批准 B 替代 A，随后撤回该次新增 B。应恢复 A 原内容及 active 状态，撤掉 B；无关条目、手写备注和水位保持原值。
2. 重建上述场景，随后批准一次对 B 的更新，再用旧收据撤回 B 的首次新增。应报告 B 冲突，保留新版 B，A 也不变。再做一组仅 A 被后续修改的用例，同样应整组退出。两组均不得新增撤回反馈。
3. 对一次成功撤回再执行一次，只产生一条撤回反馈。用缺少连带条目前像的旧收据测试，不能凭猜测恢复 A 或删除 B。
**验收条件**　无冲突时完整逆转原操作；任一受影响条目发生后续变更时整组零改动；重复撤回无副作用。必须断言 A、B 的内容和状态，不能只断言命令成功或 B 已消失。
## 四、修复回滚不完整
**修改目标**　重点检查 `governance.py`、`config_io.py`。快照记录每个受管目标原先是否存在及原始字节摘要。恢复前一次性验证清单、所有必需源文件、目标路径和摘要，再开始改盘。跨文件提交留下可在下一次启动时识别的事务记录，覆盖进程直接退出的情况。
**回归用例**
1. 正常初始化后确认水位文件不存在，执行首次 apply。回滚时显式重置水位，应恢复为“文件不存在”。另测已有水位时的默认 rollback，应保留回滚前的当前水位。同步核对主题、晋升规则、索引、编译入口及负反馈账本的预期存在性和内容。
2. 分别制造“快照缺一个必需文件”和“一个文件摘要错误”。两次均应在首次业务写入前失败；所有受管文件与回滚前逐字节一致。
3. 在独立子进程中，分别于“主题已写、编译视图未写”和“水位已写、收据未提交”两个边界强制结束进程。用正常入口重新启动，验证未完成事务恢复到提交前的一致状态；再次启动也不得重复恢复或产生新反馈。仅抛出能被当前 `except` 捕获的异常不足以覆盖此用例。
**验收条件**　恢复后逐项比对受管文件集合及 SHA-256；快照、收据和事务记录按各自预期另验。任何恢复失败都不能返回成功或留下部分恢复的业务状态。
