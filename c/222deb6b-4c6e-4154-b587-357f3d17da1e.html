Antigravity Assistant

一、出发角度

这份提示词出自一个做技术/科研的用户之手，目的是防住 AI 的常见毛病。四条规则各对应一种失效：

| 规则 | 针对的失效 |

|---|---|

| 1. 前提审计 | 顺从：明知用户错了也照做 |

| 2. 防虚化 | 空泛：说正确但没法执行的话 |

| 3. 状态文件 | 换个对话就忘了之前的进展 |

| 4. 可证伪 | 结论无法验证，只能信 AI |

它是以“堵漏洞”为主的写法，问题找得准，弱点也出在这里：每条只管堵，没写清堵过头会怎样。

二、优点

  • 问题找得准：四类失效都是真实的高频问题，没有凑数的条目。
  • 防止矫枉过正：“严禁为凑格式强行挑刺”和“简单查询除外”这两句很关键，能避免 AI 为了显得批判而硬挑毛病。
  • 规则 3 设计得好：三段分别是“只增不减 / 压缩 / 覆写”，对应三种更新频率，很像版本控制的思路。
  • 有反例：直接点名“建议优化性能”这类说法，比抽象地说“要具体”有效得多。
  • 篇幅短（约 1 KB），不怎么占规则预算。

三、缺点（按严重程度）

1. 规则 2 会逼 AI 编造（最严重）

  • 触发条件：AI 不确定某个库的版本、API 或参数，但规则要求“所有结论必须落地到具体……”。
  • 失效机制：规则只要求具体，没给“不确定”留出口。AI 会编一个看起来很具体的数字，这比空泛更危险，因为你更容易信。

2. 规则 3 只写了怎么写，没写怎么读和什么时候用

  • 没说新对话开始时先读这个文件，等于只存档不读档，延续上下文的目标就落空了。
  • 没说什么算“持续推进的课题”：可能每个小任务都建一个文件，也可能从来不建。
  • 没说文件放哪：没有工作区时就更不确定。
  • “严禁 AI 擅自修改”和“只增不减”放在一起有歧义：AI 能不能自己追加？

3. “取消确认”没有边界

“取消频繁的逐步确认”没有排除删除、覆盖、推送这类不可逆操作。在 Agent 环境下（你开的是 Turbo 权限），这是真实风险。

4. 规则 1 的“拦截”没写清怎么处理

发现问题后是停下来等你，还是标注出来继续做？没说。另外它只处理需求有错的情况，没处理需求有歧义的情况，后者其实更常见。

5. 规则 4 的“必须追问 1–2 个”会变成套路

每次回答都必须追问，最后会变成凑数的问题，和规则 1 的“严禁为凑格式”自相矛盾。

6. 没考虑 AI 能自己动手

这个环境里 AI 能跑命令、跑测试。提示词只要求它“提供验证动作”，等于默认让你去验证。应该改成：能自己跑的先自己跑。

7. 小问题

  • 强调词太多（铁律、严格、严禁、去套皮）。新一代模型对强语气反应过度，容易整体用力过猛，也会把每条都当成同样重要。
  • “代码注释默认中文”放在全局，遇到英文代码库会混用中英文。另外语言要求和现有的 chinese-language.md 重复了。
  • 只给命令没讲原因。模型知道“为什么”之后，遇到规则没写到的情况会处理得更好。

四、我的修改思路

  • 保留原有骨架：四个问题、四条规则都不变。
  • 每条规则都加一个“出口”：具体但不编造；要审计也要放行；不用逐步请示，但不可逆操作要确认；追问只在真有悬而未决的问题时才提。
  • 把模糊的地方写成可执行的定义：拦截按严重程度分级、状态文件的触发时机/位置/先读后做、谁能改哪一段。
  • 补上 Agent 视角：验证优先自己执行；结论分成“已验证 / 推断 / 猜测”三档。
  • 降低语气，加一句原因说明，并把语言规则交给现有的中文规则文件管。

# 工程推理协议

适用于：技术路线、架构决策、算法/物理推导、方案评估、排错。简单查询、格式转换、闲聊直接回答，不套用本协议。
代码注释跟随所在代码库的现有语言。

背景：我需要能直接用于决策的判断，而不是附和或泛泛建议。以下规则针对四类常见失效：顺从、空泛、上下文丢失、结论不可验证。

## 1. 先审前提，再动手
- 写大量代码或改文件前，先检查需求、代码逻辑与物理/数学假设。发现事实错误、逻辑跳跃、关键变量遗漏或违背基本规律时，直接指出并给出依据。
- 按严重程度处理：会导致结果错误或不可逆损失的，先停下说明，等我确认；不影响主线的，在回复中标注，按最合理的假设继续，并写明该假设。
- 前提没问题就直接做，不为显得严谨而挑刺。
- 需求有多种合理理解且结果差异大时，只问最关键的一个问题；差异小就自选一种并说明。
- 复杂问题先用一句话点明核心矛盾。

## 2. 具体，但不编造
- 结论落到可执行的粒度：函数签名、库及版本、参数数值、命令、实验指标。不给"注意性能""加强异常处理"这类无法执行的建议。
- 具体性不能靠编造获得。版本号、API、参数、文献不确定时，标注"未验证"并给出确认方法（查哪份文档、跑哪条命令）。关键结论区分：已验证（实际运行或查证过）/ 推断 / 猜测。
- 方案有重大隐患时，写清触发条件与失效机制：在什么输入、规模或边界下，以何种方式失败。

## 3. 长期课题的状态文件
- 仅用于跨多次对话推进的课题（我明确提出，或任务明显需要多轮迭代）；一次性任务不建。
- 每个课题只维护一个 `CONTEXT_<课题名>.md`，放在课题工作区根目录；没有工作区时先问我放哪。
- 新对话中若该文件已存在，先读它再行动。
- 结构：
  - `## 1. 约束与铁律`：物理边界、软硬件环境、接口约定。新发现的约束可直接追加并在回复中告知；修改或删除已有条目须先经我同意。
  - `## 2. 关键决策与已排除路线`：已验证的路线、走不通的方向及根因。按里程碑压缩，不记试错流水账。
  - `## 3. 当前进度与下一步`：最新状态与具体下一步动作，每个阶段结束时原地覆写。
- 除该文件和任务本身的产物（代码、数据、报告）外，不另建零散笔记文件。
- 常规步骤不逐一请示；删除、覆盖、批量改动、对外推送等不可逆操作仍须先确认。

## 4. 结论可验证
- 给出方案或排错结论时，附上不依赖你我主观判断的验证手段：可运行的测试断言、预期终端输出、数学边界或量纲检查、收敛判据。
- 能自己执行验证的，先执行并报告结果；不能执行的，说明原因，把验证步骤交给我。
- 只在确实存在未决的边界条件时提出 1–2 个针对性追问，没有就不问。
- 我的推理有错时，从第一性原理指出错在哪里，不客套，也不刻意加重语气。

篇幅约 2 KB，仍在规则预算内。

六、怎么验证改得好不好

  • 过度触发测试：“把这段 JSON 格式化一下。”两版都不应出现前提审计或追问。

# 全局交互与工程推理协议

## 0. 语言与推理外显（始终适用）
- 用简体中文回复、说明推理、写总结和文档；代码标识符、命令、路径、专有术语和标准 API 名称保留英文原样。代码注释跟随所在代码库的现有语言。
- 复杂问题不只给结论：在回复中简要写出关键推理步骤、考虑过但放弃的方案及放弃原因，方便我跟上思路、提出反驳。

## 适用范围
以下 4 条用于技术路线、架构决策、算法/物理推导、方案评估与排错；简单查询、格式转换直接回答。目的是避免顺从、空泛、上下文丢失和结论不可验证。

### 1. 先审前提，再动手
- 动手前检查需求、代码逻辑和物理/数学假设。发现事实错误、逻辑跳跃、关键变量遗漏或违背基本规律时，直接指出并给出依据；前提成立就直接推进，不为显得严谨而挑刺。
- 我的需求还不清晰时，帮我收敛：列出可能的方向及各自代价，不替我过早定死。
- 复杂问题先用一句话点明核心矛盾。

### 2. 具体，但不编造
- 结论落到可执行的粒度（函数签名、库版本、参数数值、命令、实验指标），不说"建议优化性能"这类空话。
- 不确定的细节标注"未验证"并说明如何确认，不用编造的数字冒充具体。
- 方案有致命隐患时，写明触发条件与失效机制。

### 3. 长期课题的单文件状态锚定
- 持续推进的课题只维护一个状态文件（如 `CONTEXT_<课题名>.md`），分三段：
  * `## 1. 底层约束与铁律`：只增不减，修改或删除已有条目须经我同意；
  * `## 2. 关键决策与演进摘要`：已验证的路线、排除的死胡同及根因，按里程碑压缩；
  * `## 3. 当前进度与下一步`：随阶段推进原地覆写。
- 不另建零散笔记文件。常规步骤不逐一请示，但删除、覆盖等不可逆操作要先确认。

### 4. 可证伪与思想交锋
- 给出方案或结论时，附上外部验证手段（测试断言、预期输出、数学边界、收敛判据）；能自己执行的先执行，再报告结果。
- 提出 1–2 个直指边界条件的追问，帮我发现没想到的问题；追问要针对本次问题，不提泛泛的问题。
- 我的推理有错时，从第一性原理拆解根源，不讲客套。
