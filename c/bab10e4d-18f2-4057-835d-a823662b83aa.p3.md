### 四、 唯一不能塞进 MCP 的边界是什么？（双端最小职责切分）

虽然 90% 的提示词组装都能硬编码进 MCP，但有 **2 件事是 MCP 服务端代码感知不到的**，必须以极简形式（不到 10 行）留在主模型的单系统提示词（或 `deepseek-subagent.md`）中：

1. **调用的时序锚点（When to Call）**：
   MCP Server 是被动受调方，它不知道主模型当前处于哪个思考阶段。因此主模型提示词中必须声明：**仅在【阶段 2：问题重构】并形成初步核心假设之后、【阶段 3：最终交付】落笔之前，调用一次红队工具**。
2. **参数的自包含约束（Self-Contained `question`）**：
   因为 MCP 服务端无法自动读取主模型的聊天历史，主模型在填入 `question` 参数时，必须把重构后的真问题连同**必要的物理参数、原文约束或代码上下文**完整打包进去，不能传一句 `question: "如上文所述，求该系统的稳定性"`。

### 五、 改造落地方案预览

如果采用这套**“MCP 服务端硬编码 + 双参数极简契约”**架构：

#### 1. MCP Tool Schema（收敛为极简双参数）
```json
{
  "name": "delegate_to_deepseek",
  "description": "【红队逆向探针】仅在完成『阶段2：问题重构与初步假设』后、『阶段3：最终交付』前调用。服务端已硬编码高强度红队对抗审计协议，只需传入自包含的重构后真问题(question)与初步核心假设/初稿(draft_answer)。",
  "inputSchema": {
    "type": "object",
    "required": ["question", "draft_answer"],
    "properties": {
      "question": {
        "type": "string",
        "description": "重构后的高质量真问题（必须自包含所有已知物理参数、原文边界条件或关键代码片段，严禁使用『见上文』等指代）。"
      },
      "draft_answer": {
        "type": "string",
        "description": "主模型当前的初步核心假设、推导骨架或候选方案代码，交由红队做逆向证伪攻击。"
      }
    }
  }
}
```

#### 2. 主模型侧提示词（极简路由钩子，仅需一段话）
> **【异构红队对抗路由协议】**
> 1. **时序锁**：在完成【阶段 2：问题重构】并建立初步核心假设后、进入【阶段 3：最终交付】落笔前，对于复杂逻辑、公式推导或方案设计，调用 `delegate_to_deepseek` 工具发起红队逆向攻击。
> 2. **传参锁**：仅传 `{question, draft_answer}`。其中 `question` 必须是自包含的“重构后真问题 + 完整边界条件”（子模型无对话记忆，严禁指代上文）；`draft_answer` 为你的初步核心假设或推导初稿。
> 3. **裁决锁**：子模型仅作唱反调的高并发探针，最终逻辑裁决权与综合权完全锁在你（主模型）手中。
