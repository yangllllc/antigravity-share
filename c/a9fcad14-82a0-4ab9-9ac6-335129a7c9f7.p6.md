### 二、关于你提出的“Skill 合并”：关键架构边界（放弃了什么方案）

我原本打算把功能相近的第三方技能直接物理合并（例如把 K-Dense 的 `paper-lookup` + `citation-management` 合成一个目录，把 `scientific-visualization` + `matplotlib` 合成一个目录），但在交叉审查后**主动放弃了“物理合并第三方活跃 Skill”的方案**：

- **放弃原因**：一旦拆开第三方开源包把脚本和正文缝合成新目录，它就变成私有 fork，后续上游更新 API 端点或修 Bug 时无法干净更新，只会积累无穷冲突；同时把两个 16 KB+ 的技能硬缝成一个 35 KB 巨无霸，反而会拉高单次加载污染。
- **真正稳健的两种合并方式**：
  1. **对自研/静态淘汰包 → 真正吸收合并**：
     - 把 Dream 记忆 `[MEM-PPT-002]` 的实机视频避坑 + `scientific-slides` 的英文学术汇报速查，直接并入你自研的 `course-ppt-lab`；
     - 把 `self-healing` 的验证闭环 + `deepseek-stack` 的 `ds-unstick`（同错两次必停验前提）合并为一个全新、原生适配 Windows + Antigravity 的轻量技能 `debug-unstick`（同时把已被 `/dream` 取代的 `self-improvement` 归档，并**不把只读的 `blast-radius` 硬塞进去**，避免打破只读安全边界）。
  2. **对第三方活跃技能 → “上游原样保鲜 + 自动/手动双池 + 薄壳指针”**：
     - 第三方目录原封不动；**高频 7–9 个**（`course-ppt-lab`、`ppt-master`、`uncertainty-and-units`、`paper-lookup`、`scientific-visualization`、`lieflat-less-ai-tone`、`wps-office-suite`、`markitdown` 等）留在自动发现池，并把每条 `description` 统一精简到 ≤200 字符纯触发信号；
