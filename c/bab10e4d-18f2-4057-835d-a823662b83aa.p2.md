### [T2/22 Part 1/2] Antigravity Assistant
你的直觉非常敏锐——**不仅完全可行，而且将“红队审计提示词与组装逻辑”硬编码（Hardcode）进 MCP Server 内部，让主模型只传 `{question, draft_answer}` 两个纯数据参数，在架构上绝对优于把提问方式写在主模型记忆里。**

在 Agent 工程中，这本质上是从 **“提示词级指令传递（Prompt-level Instruction）”** 向 **“协议级控制反转（Protocol-level IoC / 契约封装）”** 的架构升级。

---

### 一、 为什么把“如何提问”交给主模型是一个反模式？

在现有的 `tongji_deepseek_mcp.ps1` 与 `deepseek-subagent.md` 中，虽然服务端写了基础的 `$sysPrompt`，但仍然暴露了 `task_instruction` 参数让主模型在运行时动态编写指令。如果严格收敛到你定义的 **“【阶段 2：问题重构】→ 红队逆向攻击 → 【阶段 3：最终交付】”** 单一路由协议，让主模型自己写提问词会带来两个致命缺陷：

1. **主模型的“自我赦免偏见”（Confirmation Bias）**：
   让主模型自己写 `task_instruction` 去审查自己刚生成的“初步核心假设”，相当于**让考生自己拟定评分标准去批改自己的试卷**。大模型具有天然的自洽倾向，主模型在组装提问词时，极易下意识地加入防御性限定词（如*“在……合理假设下，请检查以下代码/推导是否有明显漏洞”*），在无形中给 DeepSeek 植入顺从暗示（Sycophancy），导致红队攻击失效。
2. **指令与数据耦合（Meta-Prompt 污染）**：
   主模型既要负责提炼“重构后的真问题”，又要分心去构思“怎么扮演一个严厉的考官去套 DeepSeek 的话”，模糊了**呈堂证供（Data）**与**审讯手段（Control）**的边界。

---

### 二、 两种架构在【稳定性】与【Token 消耗】上的本质差异

我们将这两种方案定义为：
- **架构 A（主模型组装指令）**：在主模型规则中写长篇指南，教主模型如何向 DeepSeek 提问，调用时动态生成指令。
- **架构 B（MCP 服务端硬编码封装）**：主模型只传 `{question, draft_answer}` 纯数据结构体；红队人设、攻击维度、输出格式全部硬编码在 `tongji_deepseek_mcp.ps1` 中。

| 评估维度 | 架构 A：写在主模型记忆（自然语言提示词）里 | 架构 B：硬编码在 MCP Server 代码内部（推荐） | 本质差异剖析 |
| :--- | :--- | :--- | :--- |
| **1. 红队攻击烈度与正交性** | **随上下文波动（易软化）**。主模型越自信，生成的提问词越温和，极易沦为同质化复读。 | **100% 恒定冷酷（强制正交）**。主模型只能交出“靶子”，无权干预审讯规则，彻底物理隔离主模型的确认偏误。 | **裁判权与举证权分离**：主模型举证 + 终审，MCP 服务端独立控场红队规则。 |
| **2. 长对话抗衰减稳定性** | **随对话轮数指数衰减**。对话到第 20 轮时，主模型注意力被稀释，常退化为随手传一句“帮我看看对不对”。 | **字节级确定性（Deterministic）**。无论第 1 轮还是第 100 轮，PowerShell 注入给 DeepSeek 的红队 System Prompt 永远一字不差。 | 用**确定性的代码逻辑**替代了**概率性的注意力遵循**。 |
| **3. JSON 序列化稳定性** | **较低**。主模型在 JSON 参数里混写复杂指令与多行公式/代码，容易触发转义错误或指令边界混淆。 | **极高**。只传两个纯内容字段，服务端用 `<question>` 与 `<draft_answer>` XML 标签做硬隔离，结构绝对干净。 | 降低 Tool Call 解析失败率与 Prompt Injection 风险。 |
| **4. 主模型常驻 Input Token** | **高（每轮都扣费/占窗）**。即使本轮不调工具，主模型也必须背着几百字“怎么向子模型提问”的规则说明。 | **极低（接近 0 冗余）**。所有关于“红队怎么审、按什么格式输出”的提示词全部下沉到脚本，对主模型完全隐形。 | 释放主模型宝贵的 Context 注意力预算。 |
| **5. 主模型生成 Output Token 与延迟** | **慢且贵**。每次调用工具，主模型都要现场吐出 100~300 Tokens 的元指令（Meta-Instruction），白白增加数秒等待。 | **快且省**。主模型最昂贵的 Output Token 只用于输出重构后的真问题与初稿核心假设，零废话。 | 砍掉主模型每次调用时的“元指令生成开销”，同时提升同济 API 侧的 Prefix Cache（前缀缓存）命中率。 |

### 三、 进阶架构设计：MCP 服务端的“双向硬编码封装”

顺着你的思路往下推演一步，我们甚至可以在 `tongji_deepseek_mcp.ps1` 中实现 **“双向硬编码封装（Two-Way Encapsulation）”**，把主模型侧的负担压榨到极致：

1. **下行硬编码（MCP Server $\rightarrow$ DeepSeek Flash）**：
   主模型只传 `{question, draft_answer}`。MCP 脚本内部自动将其包裹进严苛的 **红队逆向审计 System Prompt**（强制要求 DeepSeek 禁止附和、必须从【隐含前提刺破】【边界/奇点失效】【反向证伪构造】三个维度发起攻击，并锁定低温度 `temperature = 0.15`）。
2. **上行硬编码（MCP Server $\rightarrow$ 主模型）**：
   **连“主模型拿到红队结果后如何裁决”都不需要常驻在主模型记忆里！**
   我们直接把【阶段 3：主模型终审裁决锁】硬编码在 `tongji_deepseek_mcp.ps1` 的 **返回值拼接模板** 中。只有当工具真正被调用并返回结果的那一刻，这段裁决指令才会随红队报告一起动态注入主模型上下文：
