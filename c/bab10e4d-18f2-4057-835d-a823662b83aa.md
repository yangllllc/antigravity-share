### 二、 为什么 SakuraCat 刚才刚开始会“连接速度超时”？

```text
[TCP] dial DIRECT (match GeoIP/cn) 127.0.0.1:59499(codex.exe) --> chatgpt.com:443 error: connect failed: dial tcp 118.193.240.37:443: i/o timeout
```
- **根因**：SakuraCat 机场下发的订阅配置本身有缺陷——它的 `rules:` 末尾写了 `- GEOIP, CN, DIRECT`（未加 `no-resolve`），且 DNS 用的是国内阿里 DoH。当处于 **规则模式（`rule`）** 时，访问 `chatgpt.com` 会先触发国内 DNS 解析，被 GFW 污染返回一个假国内 IP（`118.193.240.37`），导致误命中 `GeoIP/cn` 去尝试直连，白白卡住超时（`i/o timeout`）！
- **这就是为什么你平时用 SakuraCat 必须开“全局模式（`global`）”**——全局模式下不做本地 `GeoIP/cn` 解析，直接把 `chatgpt.com` 交给香港节点解析，瞬间秒连。

### 一、 为什么把“如何提问”交给主模型是一个反模式？

在现有的 [tongji_deepseek_mcp.ps1](file:///C:/Users/Administrator/.gemini/config/tongji_deepseek_mcp.ps1#L25-L52) 与 [deepseek-subagent.md](file:///C:/Users/Administrator/.gemini/config/rules/deepseek-subagent.md) 中，虽然服务端写了基础的 `$sysPrompt`，但仍然暴露了 `task_instruction` 参数让主模型在运行时动态编写指令。如果严格收敛到你定义的 **“【阶段 2：问题重构】→ 红队逆向攻击 → 【阶段 3：最终交付】”** 单一路由协议，让主模型自己写提问词会带来两个致命缺陷：

1. **主模型的“自我赦免偏见”（Confirmation Bias）**：
   让主模型自己写 `task_instruction` 去审查自己刚生成的“初步核心假设”，相当于**让考生自己拟定评分标准去批改自己的试卷**。大模型具有天然的自洽倾向，主模型在组装提问词时，极易下意识地加入防御性限定词（如*“在……合理假设下，请检查以下代码/推导是否有明显漏洞”*），在无形中给 DeepSeek 植入顺从暗示（Sycophancy），导致红队攻击失效。
2. **指令与数据耦合（Meta-Prompt 污染）**：
   主模型既要负责提炼“重构后的真问题”，又要分心去构思“怎么扮演一个严厉的考官去套 DeepSeek 的话”，模糊了**呈堂证供（Data）**与**审讯手段（Control）**的边界。

### 二、 两种架构在【稳定性】与【Token 消耗】上的本质差异

我们将这两种方案定义为：
- **架构 A（主模型组装指令）**：在主模型规则中写长篇指南，教主模型如何向 DeepSeek 提问，调用时动态生成指令。
- **架构 B（MCP 服务端硬编码封装）**：主模型只传 `{question, draft_answer}` 纯数据结构体；红队人设、攻击维度、输出格式全部硬编码在 [tongji_deepseek_mcp.ps1](file:///C:/Users/Administrator/.gemini/config/tongji_deepseek_mcp.ps1) 中。

| :--- | :--- | :--- | :--- |
| **1. 红队攻击烈度与正交性** | **随上下文波动（易软化）**。主模型越自信，生成的提问词越温和，极易沦为同质化复读。 | **100% 恒定冷酷（强制正交）**。主模型只能交出“靶子”，无权干预审讯规则，彻底物理隔离主模型的确认偏误。 | **裁判权与举证权分离**：主模型举证 + 终审，MCP 服务端独立控场红队规则。 |
| **2. 长对话抗衰减稳定性** | **随对话轮数指数衰减**。对话到第 20 轮时，主模型注意力被稀释，常退化为随手传一句“帮我看看对不对”。 | **字节级确定性（Deterministic）**。无论第 1 轮还是第 100 轮，PowerShell 注入给 DeepSeek 的红队 System Prompt 永远一字不差。 | 用**确定性的代码逻辑**替代了**概率性的注意力遵循**。 |

| **5. 主模型生成 Output Token 与延迟** | **慢且贵**。每次调用工具，主模型都要现场吐出 100~300 Tokens 的元指令（Meta-Instruction），白白增加数秒等待。 | **快且省**。主模型最昂贵的 Output Token 只用于输出重构后的真问题与初稿核心假设，零废话。 | 砍掉主模型每次调用时的“元指令生成开销”，同时提升同济 API 侧的 Prefix Cache（前缀缓存）命中率。 |

### 四、 唯一不能塞进 MCP 的边界是什么？（双端最小职责切分）

虽然 90% 的提示词组装都能硬编码进 MCP，但有 **2 件事是 MCP 服务端代码感知不到的**，必须以极简形式（不到 10 行）留在主模型的单系统提示词（或 [deepseek-subagent.md](file:///C:/Users/Administrator/.gemini/config/rules/deepseek-subagent.md)）中：

1. **调用的时序锚点（When to Call）**：
   MCP Server 是被动受调方，它不知道主模型当前处于哪个思考阶段。因此主模型提示词中必须声明：**仅在【阶段 2：问题重构】并形成初步核心假设之后、【阶段 3：最终交付】落笔之前，调用一次红队工具**。
2. **参数的自包含约束（Self-Contained `question`）**：
   因为 MCP 服务端无法自动读取主模型的聊天历史，主模型在填入 `question` 参数时，必须把重构后的真问题连同**必要的物理参数、原文约束或代码上下文**完整打包进去，不能传一句 `question: "如上文所述，求该系统的稳定性"`。
