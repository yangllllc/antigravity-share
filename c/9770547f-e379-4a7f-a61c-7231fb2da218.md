### 2. 它们是怎么协作的？

Orchestrator **不是**“先分类再把整个问题发给某个模型”的路由器，也**不是**“两个模型并行独立解答再互审”。它是**单个对话、单个 Agent 内部的自动接力**：

1. **Planner 先只读规划**：收到你的消息后，Planner 先读代码、消歧义、列出执行步骤和“什么情况下要重规划”。**注意官方文档的关键细节：如果你的消息只是提问、概念讲解或复盘（不需要改文件），Planner 会直接自己回答，根本不会唤醒 Executor。**
2. **Executor 接手干活**：需要查代码、改文件、构建、跑测试时，自动切给 Executor 批量执行并自检。
3. **踩坑自动退回 Planner**：如果 Executor 遇到意外（如验证连续失败 2 次、接口行为不符、遇到计划没决定的设计分叉），控制权自动退回 Planner 查现场、改计划，再交回 Executor。
4. **收尾与插话复核**：长任务完成或你中途插话时，Executor 向 Planner 汇报，由 Planner 验收或更新计划。

### 4. 为了学习效果更好，应该怎么选？

**结论：日常学习（读《工程光学》、拆物理机制、不跳步公式推导、复述纠偏）不要选 Orchestrator。**

原因很直接：
1. **无双脑增益**：纯问答和公式推导不改文件，Orchestrator 下 Executor 根本不上场，你选 `Orchestrator (Neon Extra)` 在学习时就等于直接用 `Gemini 4 Neon (Extra)`。
2. **小脚本反而多一道交接**：学习中偶尔写个 20 行 Python ABCD 矩阵脚本或交互 HTML 光路图，交给单强模型一口气写完更快更准；让 Planner 先出计划再交接给较小的 Executor，对这种短脚本纯属脱裤子放屁。
3. **学习真正防翻车靠“异构交叉校验”**：单一模型再强也可能暗中跳步或搞混符号约定，你的“**单强主模型 + 同济 MCP**”恰好用免费校内额度补齐了跨模型验算。

#### 按场景的推荐配置

- **日常理论/光学学习（最推荐主力）**：直接选单模型 **`Gemini 4 Neon`**（日常 `Medium`/`High`，遇到硬推导开 `Extra`）+ 你的 **同济双核 MCP `v5.4.0`**。主模型负责按你的节奏讲透和出小检验，同济双核负责把机制盲区和中间推导验死。
- **真正想让 `Gemini 4 Neon (Extra)` 和 `Claude Opus 5.5 (High)` 双旗舰联动互审（仅用于高价值硬骨头）**：
  - `Orchestrator` 做不到，但原生 **`/swarm`** 可以（见 [Swarm 文档](https://antigravity.google/docs/swarm)）！你可以直接指定角色和各自模型，例如让推导 worker 跑 `Gemini 4 Neon (XHigh)`，让 `@verifier` 跑 `Claude Opus 5.5 (High)` 独立抓符号约定、近似条件和边界反例。
  - 另如果是复杂代码/算法难点攻关，可以用 `/boost` 做多轮挑战验证；超大型跨天项目再上 `/teamwork`。
  - **代价与实测避坑提醒**：① `/swarm` 每个 worker 都是完整独立 Agent，**配额烧得极快**，绝不适合每道日常习题都开；② 历史本机日志样本（2026-11-20）显示 `Claude Opus 5.5 (High)` 在长段中文物理/科普输出时曾高频触发 `STOP_REASON_CONTENT_FILTER` 误杀，如果用它当审稿人，让它输出简短精准的挑错清单或英文公式核验，比让它写长篇中文讲义稳得多。
- **什么时候开 `Orchestrator` 最香？**：做多文件编程工程、重构仿真项目、改插件/脚本并反复跑测试时——Planner 控全局质量，Executor 极速敲代码跑单测，省时又省大额配额。
