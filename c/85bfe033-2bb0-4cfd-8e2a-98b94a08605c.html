二、Antigravity 的 Drive 功能：原理、用法与对你的实际价值

前提核对：核查最新官方全量文档索引（antigravity.google/llms.txt）、v2.35.0（2026-11-23）更新日志与本机插件市场缓存 marketplace.json 后确认，Antigravity 中与 Drive 对应的是 Google Drive 官方集成，分为本地插件形态与 Remote Agents 云端挂载形态两条路线（如果你在某处看到“Drive”指代的是别的社区词或新词，贴给我我再专项核查）。

1. 底层原理（拆成两条链路）

  • 链路 A：本地桌面版 / CLI 的官方 Google Drive 插件（gdrive, v0.0.11）
  • 从你本机缓存的 marketplace.json 可以直接看到其机制：
  • 常驻 Context Provider（@drive 实时补全与链接解析）：插件注册了 "trigger": "drive" 与常驻进程 skills/gdrive/scripts/gdrive context-provider（300ms 防抖）。你在输入框敲 @drive 时实时检索云盘文件；粘贴 drive.google.com、docs.google.com（Docs/Sheets/Slides）或 colab.research.google.com/.../drive/... 链接时，正则 uriPatterns 会自动把它转成云端引用芯片。
  • 按需拉取 + OAuth 凭证隔离：@drive 提及不会把整个文档粗暴塞进 Prompt 撑爆上下文，只把文件定位符交给 Agent；Agent 真正需要读/写/下载时，通过沙箱 CLI 调用 Google Drive API，OAuth 2.0 令牌由 Antigravity 宿主加密保管并在请求时注入，不暴露给对话上下文。
  • 链路 B：Remote Agents 云端隔离项目的 Drive 资源挂载
  • Pro/Ultra 个人号开启 Remote Agents 后，Agent 跑在 Google 托管的隔离云端虚拟机（VM） 里（合盖、关机或手机访问 antigravity.google.com 都能继续跑）。
  • 因为云端 VM 读不到你本地 C: 盘，Antigravity 通过 Project Resources 让你绑定 Google Drive 文件夹/文档、GitHub 仓库或上传文件（单文件 ≤ 8 MiB、单项目 ≤ 50 文件 / 100 MiB），云端 Agent 在沙箱里按需读取这些 Drive 资源。

2. 怎么使用？

  • 用法一（本机桌面版最常用）：
  • 在左侧栏 Customizations > Marketplace 安装 Google Drive 插件（也可直接点文末卡片添加），按提示完成一次 Google OAuth 授权（经实测你当前尚未安装该插件）。
  • 在对话输入框键入 @drive + 文件关键词 选中文件，或直接粘贴 Drive / Docs / Colab 链接，然后下达检索、阅读、下载 PDF、整理文件夹等指令。
  • 用法二（云端 Remote Agents）：
  • 在左侧栏 Projects 旁点 + → New Remote Project（或手机/浏览器打开 https://antigravity.google.com 登录同一 Google 个人账号）。
  • 点击 Add Resource → Google Drive，通过 Picker 勾选要挂载的文件夹/PDF/文档即可开始云端对话。

3. 对你来说到底有没有用？（结合你的真实工作流评估）

  • 真正有价值的 2 个场景：
  • 打通两台电脑的 Zemax 跨机协作（最切合你）：你的 Zemax 装在另一台电脑上，平时需要把 .zmx、导出的 Prescription Data .txt 报告和像差/焦移截图传回本机复核。如果在两台电脑上共用一个 Google Drive 同步文件夹，在本机 Antigravity 里直接 @drive 就能自动抓取最新 .zmx/报告/截图并更新你的学习记录，省去反复手动传文件。
  • 外出开组会 / 手机端查论文 + 联调 Colab：把课题组论文 PDF 或组会资料丢进 Drive，开组会时手机开 antigravity.google.com 用 Remote Agent 挂 Drive 就能实时查论文、算参数；另外该插件原生支持解析 Google Colab 链接，以后跑较重的光学数值仿真如果放到 Colab，本机 Agent 也能直接衔接读写。
  • 局限与避坑（不建议替代本地流程的原因）：
  • Remote Agents 云端环境无法使用你本机的自定义工具链：官方文档明确说明，Remote Agents 不加载你本机的同济双核 MCP（更无法绑定同济物理校园网网卡）、本地 antigravity-dream-memory / antigravity-share-hub 插件与本地桌面文件。
  • 网络前提：读写 Google Drive 依赖稳定的代理链路（你的 SakuraCat），断代理时 @drive 会直接不可用；因此只适合做跨机文件中转与外出轻量阅读，核心学习笔记和本地脚本仍应留在你本机目录跑。

核心矛盾先说透

直觉上容易认为“Carbon 是重型旗舰、Neon 是中坚档，不差额度就该无脑选 Carbon”。但这个前提在当前版本下不成立——你实际对比的是两个不对等的组合：

  • Gemini 4 Neon 比 Carbon 晚一周发布（基于 Carbon 架构优化适配），且开放了第 4 档超高推理预算 XHigh；
  • Gemini 4 Carbon 最高只开放到第 3 档 High（本机实测可选档位只有 Low / Medium / High，无 XHigh）。

因此，拿 满血 Neon (XHigh) 对撞 非满血档位的 Carbon (High)，并不是“小杯打大杯”，实测公开基准上 Neon (XHigh) 在绝大多数硬指标上反而反超了 Carbon (High)。

为什么选 Neon (XHigh)，放弃 Carbon (High)？

结合你日常的真实任务结构（光学专业课与公式推导学习、光学平台物理直觉建立、Python/HTML 交互仿真、Zemax 参数分析、Antigravity 脚本与插件工程），Neon (XHigh) 胜出有三个纯效果层面的理由：

  • 核心能力面直接压过 Carbon (High)

你最常撞上的两类核心需求——多步数理推导（对应 RiemannBench、HLE-Diamond）和科研代码/仿真脚本一次性写对（对应 Terminal-Bench-Science、CursorBench 4.1）——恰恰全是 Neon (XHigh) 分数更高、领先幅度最明显的区间。

  • 指令遵循与复杂规则执行更稳（Steerability）

你配置了严格的全局推理协议与分步教学约束（如不跳步、区分实测与推断、按学习起点控制节奏）。作为后发优化版本，Neon (XHigh) 在严格按自定义提示词格式和节奏输出方面，普遍比早期重型底座更不容易“自顾自讲偏”或擅自堆砌超纲术语。

  • 交互流畅度本身就是学习效果的一部分

即便额度无限，Neon 的生成与思考吞吐约是 Carbon 的 2 倍（第三方实测约 ~110 tok/s vs ~55 tok/s）。学习光学时很多突破靠的是高频连续追问（“为什么这里取负号 → 我复述一遍你帮我纠偏 → 出道 3 分钟手算题”），Carbon 单轮动辄更长的等待会打断思维连续性，间接降低每小时吸收效率。

放弃 Carbon (High) 的代价与结论失效边界

把 Carbon (High) 排除在唯一主力之外，唯一真正的损失在于：

  • 当任务进入极高难度的前沿开放物理推导（接近 CritPt 这类无现成套路的硬物理题），或需要连续几十步工具调用、跨越半小时以上的超大型代码库自主重构时，Carbon (High) 的底层重模型红利会显现出来——它在极长推理链后半段更抗漂移、更不容易为了凑出结论而“偷偷走捷径”。
  • 失效触发条件：如果你后续使用中发现，自己高频卡壳的不是《工程光学》和仿真脚本，而是大量无标准答案的前沿论文理论推导/多物理场复杂建模，且 Neon (XHigh) 在深追问到第 4–5 轮时开始出现前后逻辑自相矛盾，那么这个“选 Neon”的结论就会反转，应改切 Carbon (High)。
