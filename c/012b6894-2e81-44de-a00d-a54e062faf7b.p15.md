## 二、三项工程修复要点与测试对照

### 核心改动摘要
1. **批复错版（`governance.py`、`review_ui.py`、`dream_cli.py`）**：
   - `stage_proposal` 拒绝重复 `op_id`，绑定 `manifest_hash` 与 `processed_batches`，计算不可变 `plan_hash`，冻结每版产物至 `runs/<run_id>/plans/<plan_hash[:16]>/`，并将 `plan_hash` / `manifest_hash` 嵌入 `staged_plan.json`、`review_summary.md` 与 `review.html`（在线提交与离线导出一致）。
   - 三审阅通道共用 `_validate_decisions_payload`：强校验 `run_id`、必填 `plan_hash`（缺版本号的旧批复直接拒收要求重审）、`manifest_hash`、唯一/已知/完整 `op_id` 集合与合法决议值；**缺项保持待审拒绝落盘，不记为驳回、不写负反馈**；在线 HTTP 在校验通过前不覆盖 `decisions.json`，陈旧版本返回 HTTP `409`。
   - 幂等性：按 `runs/<run_id>/receipts/<plan_hash[:16]>.json` + `decisions_hash` 识别重复提交，直接返回原收据且零副作用；保留原有 `base_hash` 漂移检查。
   - 批次水位：通过 `state/batch_progress.json` 跟踪每个 `run_id` 已完成批次，仅当某会话在 `manifest.json` 内的全部分片均已处理（含显式零候选）时才推进该会话水位。
2. **revert 误删（`governance.py`）**：
   - `_apply_op_to_doc` 规范化并记录操作触及的全部条目（含被 `supersedes` 改写的旧条目）前后像至 v2 收据的 `affected_entries`。
   - `revert_item` 在锁内先逐条比对所有 `affected_entries` 的当前磁盘状态与收据 `after_entry`，任一条目（B 或 A）发生后续变更即整组中止并列出冲突字段，零写盘、零新增反馈；无冲突才整组还原并在收据标记 `reverted: true`（二次撤回幂等，仅产生 1 条撤回反馈）；缺少连带条目前像的旧收据明确拒收。
3. **回滚不完整（`config_io.py`、`governance.py`）**：
   - 快照 v2 完整登记全部固定受管目标（`promoted_rules.md`、`INDEX.md`、`state/watermark.json`、`state/batch_progress.json`、`state/feedback_ledger.jsonl`、`compiled/AGENTS.md`）及 `topics/*.md` 的 `exists` 标志与原字节 SHA-256；恢复前由 `_verify_snapshot` 一次性校验清单、所有必需文件、规范受管路径与字节摘要，通过后才使用 `atomic_write_bytes` 还原存在文件并删除原先不存在的受管目标（如首次 apply 前不存在的 `watermark.json`）。
