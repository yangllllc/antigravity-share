二、为什么会「任何问题都回答不了」，且一换节点就好？

  • 直接根因（实测支撑 + 架构机制）

Antigravity 桌面版的后端进程 language_server.exe（见 main.log 启动参数）每次发消息都必须走本机代理（http://127.0.0.1:12450 / tun0）去连 Google 云端接口：

  • https://daily-cloudcode-pa.googleapis.com
  • https://generativelanguage.googleapis.com

当原节点 🇯🇵|日本星链家宽-IEPL 02 出现严重丢包或上游断流时（15:05 已测出 7.37 s 卡顿与 8 s 超时），请求在网络握手/传输层就直接卡死或断开——所以跟问题内容、新旧对话无关，连「你好」都发不出去。

  • 换节点同时修复了什么（实测 + 推断）
  • 实测已确认：切到 日本优选 后，出口链路切换，且 sing-box.exe 于 15:11:29 重新拉起（PID 从 22552 变为 24180），旧链路上的僵死/半开连接随之清空。
  • 未验证（日志已被重启清空）：language_server.log 每次重启 Antigravity 都会被截断清零（当前为 0 字节），且重发消息覆盖了同序号 step，因此无法事后核对 15:09–15:10 那 3 次失败的精确底层错误码（是纯网络超时 DEADLINE_EXCEEDED/TLS 断连，还是该节点短暂触发 Google 边缘节点拒连/503）。不过结合 15:05 的 7.37 s / 8 s 超时实测，节点断流拥堵是头号原因，次级可能是旧节点短时 IP 波动。

刚顺手测了一下你目前正在用的 日本优选（154.64.226.148）：

  • 路由/延迟偏抖：经系统代理 127.0.0.1:12450 访问 generativelanguage.googleapis.com 刚才单次飙到 5.27 s（daily-cloudcode-pa.googleapis.com 为 0.83 s，经 tun0 分别为 0.76 s / 0.58 s）；

建议后续如果感觉变慢或网页端 Gemini 卡顿，换到一个手动固定的低延迟原生/家宽节点（如 🇯🇵|日本原生-IEPL 01、🇯🇵|日本星链家宽-IEPL 01 或 🇰🇷|韩国家宽-IEPL 01），少挂自动分组的 日本优选。
