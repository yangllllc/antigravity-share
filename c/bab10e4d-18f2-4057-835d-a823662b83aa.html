一、 为什么把“如何提问”交给主模型是一个反模式？

在现有的 tongji_deepseek_mcp.ps1 与 deepseek-subagent.md 中，虽然服务端写了基础的 $sysPrompt，但仍然暴露了 task_instruction 参数让主模型在运行时动态编写指令。如果严格收敛到你定义的 “【阶段 2：问题重构】→ 红队逆向攻击 → 【阶段 3：最终交付】” 单一路由协议，让主模型自己写提问词会带来两个致命缺陷：

  • 主模型的“自我赦免偏见”（Confirmation Bias）：

让主模型自己写 task_instruction 去审查自己刚生成的“初步核心假设”，相当于让考生自己拟定评分标准去批改自己的试卷。大模型具有天然的自洽倾向，主模型在组装提问词时，极易下意识地加入防御性限定词（如*“在……合理假设下，请检查以下代码/推导是否有明显漏洞”*），在无形中给 DeepSeek 植入顺从暗示（Sycophancy），导致红队攻击失效。

  • 指令与数据耦合（Meta-Prompt 污染）：

主模型既要负责提炼“重构后的真问题”，又要分心去构思“怎么扮演一个严厉的考官去套 DeepSeek 的话”，模糊了呈堂证供（Data）与审讯手段（Control）的边界。

  • 架构 A（主模型组装指令）：在主模型规则中写长篇指南，教主模型如何向 DeepSeek 提问，调用时动态生成指令。
  • 架构 B（MCP 服务端硬编码封装）：主模型只传 {question, draft_answer} 纯数据结构体；红队人设、攻击维度、输出格式全部硬编码在 tongji_deepseek_mcp.ps1 中。

四、 唯一不能塞进 MCP 的边界是什么？（双端最小职责切分）

虽然 90% 的提示词组装都能硬编码进 MCP，但有 2 件事是 MCP 服务端代码感知不到的，必须以极简形式（不到 10 行）留在主模型的单系统提示词（或 deepseek-subagent.md）中：

  • 调用的时序锚点（When to Call）：

MCP Server 是被动受调方，它不知道主模型当前处于哪个思考阶段。因此主模型提示词中必须声明：仅在【阶段 2：问题重构】并形成初步核心假设之后、【阶段 3：最终交付】落笔之前，调用一次红队工具。

  • 参数的自包含约束（Self-Contained question）：

因为 MCP 服务端无法自动读取主模型的聊天历史，主模型在填入 question 参数时，必须把重构后的真问题连同必要的物理参数、原文约束或代码上下文完整打包进去，不能传一句 question: "如上文所述，求该系统的稳定性"。
