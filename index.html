三、同济优先 + 智谱回退：最小改动方案

1. 核心矛盾与 Node 22 直连选型

核心矛盾是：在 SakuraCat（tun0 172.19.0.1）/ SDKDNS（mihomo 198.18.*）并存且可能开启系统代理的 Windows 环境下，既要强制同济流量绑定物理校园网卡直打内网 VIP 10.67.0.251/252 防 403，又要保证现有 glm-4-flash 的公网普通路由与 Node SEA 单文件打包完全不受污染。

  • 拟采用方案：Node 22 原生 node:https（每请求 agent: false 独立短连接）
  • 为何放弃 undici.Agent：仓库已有前车之鉴（见 http.ts#L200-L202 与 telegram.ts），Node 22 内置 undici v7 与 node_modules/undici v8 混用会抛 InvalidArgumentError: invalid onRequestStart method，且在 SEA 单文件 esbuild CJS 打包中额外引入版本兼容风险。原生 node:https 零第三方依赖、完全忽略 HTTP_PROXY/HTTPS_PROXY/ALL_PROXY 和全局 ProxyAgent，且能精确分离建连/TLS 握手与响应体读取超时。
  • 直连穿透关键实现细节（新建 src/server/enrich/tongji-transport.ts）：
  • 固定协议与关思考：固定打 https://agi.tongji.edu.cn/v1/chat/completions，强制 model: "DeepSeek-V4.1-Flash"，请求体必带 chat_template_kwargs: { enable_thinking: false, thinking: false }。
  • 物理校园 IPv4 出口绑定：每次请求前实时枚举 os.networkInterfaces() 的非内部 IPv4：
  • 名称白名单匹配：/WLAN|Wi-Fi|以太网|Ethernet|本地连接/i；
  • 名称黑名单排除：/Meta|wintun|TAP|VPN|vEthernet|Loopback|sing-tun|mihomo|Tailscale|WireGuard|ZeroTier|\btun\d*\b/i；
  • IPv4 黑名单排除：169.254.*、198.18.*、172.19.*、127.0.0.1（保留 100.64.0.0/10，因本机实测校园 WLAN 即为 100.78.136.128，而 Tailscale 由网卡名黑名单拦截）。
  • 应用层双 VIP 轮询与 ≤5s 建连硬顶：
  • 绕坑说明：Node 22 在 autoSelectFamily: false 下，单个 https.request 的 lookup 即使返回多地址也只会连第一个。因此改为应用层明确最多 2 次独立 https.request 建连尝试（按轮询游标依次尝试 10.67.0.251 / 10.67.0.252，每次建连+TLS 握手定时 ≤2.5s，总建连严格 ≤5s）；
  • 自定义 lookup 同时兼容 options?.all === true（返回 [{ address: vip, family: 4 }]）与单地址回调，强制 family: 4, autoSelectFamily: false，保留 servername: "agi.tongji.edu.cn" 与 rejectUnauthorized: true；
  • 防双扣铁律：仅在 secureConnect 完成前（尚未发送任何请求字节）建连失败时才切换备用 VIP；一旦 TLS 建连成功并写出请求体，严禁换 VIP 重试。
  • 总超时与句柄回收：独立 AbortController 控制总请求超时 28s（25–30s 可配），覆盖建连、响应头与完整 JSON 响应体读取；finally 必清理 connectTimer、totalTimer 并销毁异常响应流。

2. 路由、回退、冷却与隔离设计（新建 src/server/enrich/ai-router.ts）

  • 严格隔离：glm-4-flash 继续走 settings.key = 'ai' 的独立 baseUrl / apiKey / model 与普通 fetch，绝不经过 tongji-transport.ts；POST /api/ai/test（草稿连通测试）显式传 skipTongji: true 保证只测表单里的智谱/备用草稿；另增 POST /api/ai/tongji/probe 供手动清冷却并单次实测同济。
  • 即时透明回退：同济返回 401/402/403/429/5xx、无物理网卡、建连/总超时、网络错、非法响应或空 content（含仅有 reasoning_content 而无 content）时，本次调用立即透明回退至 glm-4-flash；reviewItems 外层重试（attempt === 1）显式传 skipTongji: true，避免坏 JSON 重复打同济。
  • 分级冷却与退避：
  • 遇 401/402/403、无可用物理 IPv4 网卡、或双 VIP 均建连不可达（离校典型特征）→ 触发进程内长冷却（默认 8 分钟，5–10 分钟可配），期间零等待直走 glm-4-flash；支持手动重探清除，或到期后由单飞行锁放行 1 次自动重探。
  • 遇 429 / 5xx → 触发短退避（优先遵从 Retry-After 响应头并钳位在 15–120s，否则默认 60s），期间直接走 glm-4-flash，不连续撞限流墙。
  • 非阻塞并发闸门（≤2）：进程全局维护同济并发计数器（上限 2），使用非阻塞 tryAcquire()——若已有 2 路同济在跑且 glm-4-flash 就绪，第 3 路直接溢出走 glm-4-flash（零排队等待，仅无备用通道时短暂排队），finally 保证所有异常/中止路径释放槽位。
  • 单通道就绪态处理：aiReady(s) 仍尊重主开关 s.enabled；开启时只要「智谱就绪 或 同济有 Key 且未冷却未超预算」即返回 true。若仅配同济无智谱且恰遇离校，路由器返回明确类型 unavailable，不误标条目永久失败，待回校后自动恢复补译。

3. 共享周额度（1000 积分/周）预算软上限建议

  • 口径说明（实测 vs 未验证）：
  • 实测 release/data/radar.db 近 4 日日均新增 ~412 条/天，batchSize=5；外文预译 + 审核 + 单条深度译日常大约 40–90 次请求/天，单批估算约 1,500–2,500 tokens/次（推断）。
  • 同济平台 DeepSeek-V4.1-Flash 的精确「token ↔ 积分」扣减费率当前未验证，因此不强行假设 1 请求 = 1 积分，而是同时记录精确的 req_count 与 token_est（优先取接口返回的 usage.prompt_tokens + usage.completion_tokens，缺省按 Math.ceil((inChars + outChars) / 2) 估算），以本地周一 00:00 为周重置锚点持久化到 SQLite。
  • 保守默认值建议（均支持网页与 .env 热调）：
  • 日请求软上限：100 次/天
  • 周请求软上限：450 次/周
  • 周 Token 软上限：1,200,000 tokens/周（任一达标即自动无缝切回 glm-4-flash，给本机同济 MCP 留出充足周裕度；跑一两天后可对照学校控制台实际积分消耗一键调大/调小）
  • 扣费时机防双扣：仅当同济实际返回 HTTP 200（服务端确已执行推理，包括空 content / 仅 reasoning_content）时，通过 BEGIN IMMEDIATE 原子累加 SQLite 计数；403/离校/建连超时/并发溢出直切智谱时不扣同济预算。

一、二次深度审查揪出并已提前修正的 5 处真实坑点

动手前逐行核对 security.ts、feedQuery.ts、App.tsx 与 ai-settings.ts 时，发现 5 个若按初版直接写会导致功能失灵的隐蔽问题，已在本次实现中全部封死：

  • 浏览器 10 秒公有缓存会吞掉刚点开的历史：security.ts 原对未带 Cookie 的 GET /api/items 下发 Cache-Control: public, max-age=10。如果刚点开帖子立刻切去「最近浏览」，浏览器会返回 10 秒前的旧缓存导致新记录“消失”。已对 preset=history / history=1 豁免公有缓存，强制 private, no-store。
  • 默认 sort=newest 会覆盖历史倒序：feedQuery.ts 原总是携带 sort=newest，会导致服务端 applyChannelQuery 里 history 的默认 sort: "viewed" 不生效（历史按发布时间而不是打开时间排）。已改为切换「最近浏览」自动切 sort=viewed，且关闭跨源 merge 与 3 天 focus 截断。
  • 非情报流页签下「最近浏览」入口会消失 & 键盘翻页触发 429：App.tsx 在非 feed 页签硬编码只显示 starred/hidden，已补齐 history；同时 security.ts 原把所有 POST 归入 60 次/分钟写限流桶，快速按 ↓ 浏览会挤占收藏/已读配额，已把 /view 单独归入 240 次/分钟读桶并加前端 2s 去重。
  • 单配同济无智谱 Key 时单条翻译会被拦死：ai-settings.ts 的 translateSingleItem 原先硬判 !s.baseUrl || !s.model || !s.apiKey 直接报错，未给同济放行；且 config.ts 静态读取 TONGJI_API_KEY 会妨碍运行时隔离测试。已改为动态读取 getTongjiApiKey()，并在 aiReady() 与 translateSingleItem() 同时识别同济与备用通道（同时严格尊重主开关 s.enabled）。
  • 同济双 VIP 切换绝不在发出请求体后重试：tongji-transport.ts 在原生 node:https 上严格等 TLSSocket 的 secureConnect 完成后才执行 req.write/end，确保首 VIP 建连前失败切换备用 VIP（总建连 ≤5s）绝不会造成一次请求重复计费。
