1. DuarteSantos8/openGym：原理与对健身的实际帮助

它是什么、底层怎么运作（[实测] README.md）

它本质上是开源、永久免费、无广告无遥测版的 Strong / Hevy / FitNotes（AGPL-3.0），定位非常纯粹：力量训练（器械/自由重量/自重）与体重进度追踪。

  • 架构极简，可单机也可自托管：前端是 React 19 + Vite + Zustand，通过 Capacitor 直接打成 iOS（App Store，带 Apple Watch） 和 Android APK（315–760 MB，内置动画包）。你完全可以只在手机上离线单机用，不需要服务器和账号；只有想手机/电脑多端同步时，才用 docker compose up 自建（nginx + 纯 node:http 后端，连数据库都不需要，每人的数据就是一个 ./data/state-<user>.json）。
  • 同步与隐私原理：自建版用 Passkey（Face ID / 指纹） 鉴权，私钥不出手机；多端同步采用版本乐观锁 + 字段级时间戳合并（提交携带上次 revision，冲突返回 409 由客户端按字段最新时间戳合并，并保留删除标记防误复活）。
  • 核心“功效”来自确定性算法，默认零 AI：所有训练计算都在 frontend/src/lib/ 的纯函数里完成，核心原理是帮你把“渐进超负荷（Progressive Overload）”量化落地：
  • 5,600+ 动作库与灵活排课：内置 PPL（推拉腿）、上下肢、全身、5×5 模板；除了按星期排，还支持 A/B/C 轮换制（某天忙没练，下次自动接下一个，不怕整周节奏崩掉）。
  • 自动渐进规则引擎：支持线性递增、Greyskull LP、双渐进（先加次数再加重）、三渐进（次数 → 组数 → 重量），每次给出的目标重量都会明写计算理由；没做满目标次数不会瞎加重，连续卡平台自动提示减载周（Deload）。
  • 实战细节很强：按所在健身房实际有的杠铃片/器械配重阶梯算配片（Plate Math）、记 RIR/RPE、e1RM 曲线、结构平衡比例、3 模式肌肉热力图（已练容量 / 恢复中 / 长期漏练）、器械被占时一键换备选动作且保留组次、双向同步 Apple Health / Health Connect / 手表心率与锁屏实时活动。
  • AI 教练与 MCP 默认关闭：只有手动填你自己的 API Key 或 Ollama 才会开启。

对你健身有没有帮助？

  • 强推荐的场景：你在健身房或居家做撸铁/自重增肌增力，常忘记上次推了多少公斤、该不该加重，又不想给商业记录软件交月费——它能直接替代付费 App。建议先打开官方免安装网页 Live Demo 点两分钟试手感，满意直接下手机客户端单机用即可。
  • 帮不上大忙的场景：① 如果你的目标是跑步有氧或精细算每日摄入热量，它没有食物热量库；② 如果你是零基础需要视频跟练与纠正动作发力，它只有小尺寸动图，没有教练口令视频；③ [未验证项] README 明写支持 26 种语言并单列了繁体中文（Traditional Chinese），但未直接检出其静态 locales 文件列表，简体中文翻译完整度建议在 Live Demo 的设置里切一下实测确认。

3. hashgraph-online/hol-guard：这个防火墙对我们有没有用？

你的直觉非常准确——“我们没设 ≠ 需要补”，实测完它的技术规格后，结论很干脆：现阶段完全不需要安装。

原理

它是一个本地优先的 Rust 匹配引擎 + Python CLI 拦截层，通过接入各个 AI Agent 的原生 Hook（如 PreToolUse、PermissionRequest）或受控 MCP 代理，在 Agent 执行危险 Shell 命令、读取凭据文件（.env / SSH / AWS 密钥）、跑 npm/pip 安装恶意包或调用 MCP 前，按策略做出 allow / ask / block 判定并留存审计回执；同仓库还附带一个面向插件开发者的静态扫描工具 plugin-scanner。

为什么现阶段对我们几乎没有实际收益（[实测] 源码文档）

  • 在 Antigravity 上目前是“半残观测态”，拦不住最核心的风险：
  • 虽然它的 README 把 Antigravity 列进了支持名单，但查阅它自己的 antigravity-harness-support-spec.md 和 harness-support.md 后发现：
  • Antigravity 当前评级仅为 observe_only_degraded（降级仅观测模式）；
  • 官方明确写死：shell commands are not observable through the Antigravity hook surface（完全看不见、也拦不住 Antigravity 跑的任何终端命令），且 Native Approval: ❌、Resume: ❌；
  • 它最关键的 MCP 代理拦截（hol-guard mcp-relay）和 Subagent 隔离都还停留在 Phase 1 / Phase 2 Roadmap（尚未落地）；
  • 连它的 Skill 目录扫描范围都只认 .gemini/antigravity/skills/、.gemini/config/plugins/*/skills/ 和工作区 .agents/skills/，根本没扫你存放主力自建技能的 C:\Users\<USER>\.gemini\config\skills\。
  • 在 Codex 端你已经有更低摩擦的原生硬锁：
  • hol-guard 对 Codex 倒是支持完整的 PreToolUse 拦截，但根据 CONTEXT_skill_ablation.md，你的 Codex 刚刚瘦身到只留 4 个只读审查/引文技能，无头调用也已用 --sandbox read-only + 禁用 MCP 锁死了写权限和外部调用。
  • 真实威胁面不匹配，引入反而徒增故障点：
  • 你的主要工作是科研学习、自用脚本和少量已审计插件/单一内部 MCP，既没有接入邮箱/银行/生产云数据库的读写 MCP，也没开 YOLO 模式批量拉陌生三方包。相反，在 Windows 上再叠一层 pipx + Rust 守护进程 + 改写 .codex/config.toml Hook，反而增加误报和启动链排查成本。
  • 未来唯一值得启用它的条件：① 你打算让 Agent 无人值守跑陌生开源代码、或接入高权限外部读写 MCP；② 或者你准备安装一个来历不明的第三方 Agent 插件时，可以临时只跑它附带的静态扫描命令 plugin-scanner scan <插件目录> 做一次性离线体检，不必装常驻防火墙。

你的感觉是对的——这套方法论的 4 根支柱，你现在的配置已经全部涵盖，而且比它更严谨：

| 文章里的做法 | 你现有的对应机制 | 对比判断 |

| :--- | :--- | :--- |

  • 真正可取的一点习惯：推进多阶段长任务时，每做完一个里程碑并把新断点写回 CONTEXT_*.md，就干脆新开一个干净对话（例如直接发 @CONTEXT_xxx.md 推进当前下一步，完成后原位更新断点）。这样既省上下文、防注意力稀释，也能绕开 Antigravity 旧对话沿用旧规则快照的已知边界。
  • 要避开文章的一个盲区：它说“你不必盯着，让 AI 自己实时保存进度”，但全文缺少外部验证与防错门禁。如果用在你的物理推导或脚本改造上，没有你现有的“外部验证断言 + 双次失败即停 + 跨模型审稿”，AI 一旦把半对半错的中间结论实时写进进度文件，反而会把错误固化传染给下一轮新对话。

5. MICAHFANG/agy-swarm-forge（10★，v1.4.0）：原理拆解与可借鉴零件

你挑得非常准——这个仓库虽然刚起步（10 Stars），但是原生写给 Google Antigravity 2.0（同款 Gemini 4 Neon/Hydrogen + Claude Sonnet/Opus 5.5 生态）的，作者的工程抽象质量远高于一般玩具插件。我直接浅克隆并读完了它的全部规则、5 个技能和 3 个脚本。

它的底层原理（[实测] 仓库源码）

它围绕“把中大型 TypeScript 全栈项目（Next.js + Hono + Drizzle/PGSQL + Redis）从 60 分拉到 95 分”串起了一条 4 阶段自动化工程流：

  • 确定性 AST 图谱 + 错题本（ts-repo-wiki + SessionStart Hook）：
  • scan_ts_graph.mjs 调用项目本地 typescript 编译器 API（无依赖时降级正则），零 Token 消耗秒出 COMPONENT_INDEX.md（导出组件与 variant/size/slot Props）、MODULE_GRAPH.md、graph.json（含 importedBy 反向依赖用于查爆炸半径）以及离线可交互的 graph-viewer.html。
  • 配合增量覆写的 SYSTEM_PATTERNS.md 和 ≤30 条硬上限的 PITFALLS.md 错题本。
  • 先探测实证再拷问（grill-spec）：
  • 明确禁止拿两类问题打扰用户：① 读源码就能查到的事实；② 跑一条命令 / 写 10 行脚本就能分出高下的技术分叉（Empirical Forks）。把 ask_question 100% 留给产品/交互取舍，落盘 30–60 行极简验收契约 .agents/specs/*.md，取代冗长的技术实现计划。
  • 跨家族异构 Swarm + 两级有界验证（swarm-delivery + strict-review）：
  • 用 gemini-3.8-flash-medium 做 scout/wiki，gemini-4-hydrogen-high / neon-high 做并发 author-*，claude-sonnet-5-5-high（高危升 opus-5-5-high）做只读对抗式 reviewer。
  • 6 字段 NEVER 派单契约（JOB / INPUT & OWNED FILES / REUSE & NEVER / DONE WELL / HANDOFF / ESCALATE IF）锁死文件所有权和禁区；
  • 两级有界验证：author 阶段严禁跑全仓测试，只跑本领域单测（超时 ≤30s）；reviewer 阶段才按 graph.json 影响面跑唯一一次集成检查（超时 60–90s）并按 100 分制证据制打分（≥90 放行）；
  • 最多 2 轮熔断 + Attack the Premise：满 2 轮未过禁止第 3 轮盲改，退回主控先质疑前两轮共享的底层前提。
  • 开源标杆寻优（arch-best-practices + find_gold_repos.mjs）：
  • 4 份全栈参考手册 + 过滤 awesome/tutorial/demo/starter 玩具仓的 GitHub 检索脚本。

为什么绝对不要直接整包安装？（[实测] 5 处初创硬伤 / 水土不服）

  • Windows 实测直接失效：install.sh 与 hooks.json 指向的 scripts/session_start.sh 是纯 POSIX Shell + jq，在你的 Windows 环境下 Hook 跑不起来；find_gold_repos.mjs L36 甚至残留了作者私人环境里的 fish 命令与拼错的环境变量名 GITHUBT_ACCESS_TOKEN_AGY。
  • 会污染并挤占你现有的全局规则预算：它的 rules/AGENTS.md 是 always_on 的，直接把你固定成“TS 全栈工程师”，强推查 .agents/wiki/ 与强制 Swarm，与你当前的光学/科研场景及 core-reasoning-protocol.md / cross-model-reviewer.md 冲突，还会吃掉 Antigravity 全局 20k token 的规则限额。
  • 踩中了你本机已实测避过的 Opus 中文拦截大坑：它的 strict-review 让 claude-opus-5-5-high 用中文写审稿报告，也没有派前 swarm(action="models") 预检与双稿熔断——你本机在 Vertex 通道已实测 Opus 长段中文 29 次请求拦 26 次，你现有的 cross-model-reviewer.md（强制简洁英文 ≤350 words 回执 + 预检 + 熔断）在这点上比它成熟得多。
  • 技术栈强绑定：核心资产约 70% 写死在 Next.js / Drizzle / PGSQL / Hono / Redis / UI Variant 上，对 Python 科研、光学推导和轻量脚本几乎无用。
  • 未认证 API 脆弱：find_gold_repos.mjs 无 Token 裸调 GitHub Search API，在代理共享 IP 下极易触发 403 限流（刚才拉取这三个仓库元数据时就已实测撞限）。

真正值得“拆零件”吸收的 3 个好思路

  • 把“Empirical Forks（实证可判的技术分叉）”彻底排除出提问清单（来自 grill-spec）：以后用 grilling 或技术对齐时，凡是跑个 10 行脚本、看下日志或 tsc/pytest 就能分胜负的技术路线，先自己测出结果再汇报，不把这类问题抛给你拍板。
