一、deepseek-stack 真正值得我们学的 5 个思路（精炼提炼）

这个仓库名义上是给 DeepSeek 当拐杖，但剥离掉 7 个团队 GitHub PR 流水线技能和已被我们覆盖的部分（如 ds-jury 已被同济双核 MCP 覆盖、ds-unslop 已有更强的中文 lieflat-less-ai-tone、ds-swarm 已有原生 swarm）后，它有 5 个元设计对强主力模型同样极具杀伤力：

  • 双次失败即停的前提爆破（ds-unstick）：同一个报错修了两次还复现，禁止做第 3 次微调。必须停手写出前两次共享的隐含前提（比如“我改的这个文件真的在运行吗”“环境变量真的生效了吗”），用最便宜的探针做 Yes/No 实测证伪，必要时 git checkout/stash 清现场换机制。强模型在环境坑、缓存坑里一样会钻牛角尖，这是全库最值钱的机制。
  • 外部真值 5 级举证阶梯（ds-blast-radius + ds-mode）：把“我觉得没问题”拆成 L1 口述 → L2 指明 file:line → L3 路径推演 → L4 写小脚本运行反证 → L5 实机复现，并要求结论显式区分 measured / inferred / guessed。
  • 不缺额度时的终极增效器——盲评与局部嫁接（ds-best-of-n）：对高价值任务（关键算法、复杂重构、重要 UI），用隐藏评分细则跑 3–5 个隔离工作区（Antigravity 原生支持 swarm(workspace:"share", n:3)），先运行淘汰不能跑的，选架构最好的作底座，只把其余方案里的单个亮点函数或边界测试局部嫁接进来，绝不整文件合并。你既然不缺额度，这是把算力直接兑换为质量上限的最稳方法。
  • 把确定性轮询封装为黑盒脚本 + 退出码（ds-watch-pr）：全库唯一带脚本的技能，用 watch_pr.py 输出精简变化行与 0/1/2 退出码，不让 LLM 自己写循环、读大段原始 JSON 污染上下文。
  • 反规则膨胀的五级硬固化（ds-lessons）：核心理念 *"An instruction an agent can skip is a wish"*——重复 ≥2 次的错误按 架构结构 > 类型约束 > Lint/CI/Hook > 行为测试 > 文字规则 固化，且一旦硬约束生效，删掉对应的自然语言规则。这恰恰和我们接下来要讨论的“规则/记忆膨胀”形成正面呼应。

二、先补齐底层知识：Skill 到底是怎么运行的？为什么装了经常没用到？

结合 Antigravity 官方文档（skills.md、rules.md、hooks.md、customization-discovery.md）与你本机的实测配置，Agent 定制系统实际上是四层完全不同的加载机制：

| 机制 | 启动/每轮默认注入什么？ | 何时生效？ | 触发可靠性 |

| :--- | :--- | :--- | :--- |

| Rules (always_on) | 全文直接注入系统提示词（单文件上限 24 KB，总预算 20,000 token，超额自动把最大文件降级成路径指针） | 每一轮都强制在场 | 最高（但在规则过多时会出现中段注意力稀释） |

| Rules (glob / model_decision / manual) | glob 按文件后缀匹配注入；model_decision 只注入路径+一句话描述；manual 仅在用户 @ 提及时注入 | 匹配路径 / 模型自己觉得该读 / 用户显式 @ | glob、manual 高；model_decision 低 |

| Skills (SKILL.md) | 只注入 name + description + 文件路径（即渐进式披露 Progressive Disclosure），正文和脚本默认完全不加载 | 两种入口：① 模型扫一眼 <skills> 列表自己决定调 read_file；② 用户手动输入 /skill-name | 自动触发本质等同于 model_decision（偏低）；手动 /skill-name 为 100% |

| Dream 分层记忆 | Tier 1 索引表通过 always_on 规则常驻（≤140 行）；Tier 2 topics/*.md 按需 read_file | 遇索引命中领域时按需读取 | 中高（因为索引表极短、条目清晰） |

| Hooks (hooks.json) | 不占系统提示词；由宿主在 SessionStart / PreToolUse / PostToolUse / PreInvocation / PostInvocation / Stop 强制跑外部脚本 | 宿主生命周期节点确定性拦截/注入/阻止提前停止 | 100% 确定性（绕过模型自觉） |

为什么你装了一堆 Skill，干活时却常常根本没触发？

有 3 个结构性原因，而且在你本机已经拿到了直接实证：

  • 强模型的“自信跳过效应”（本机已有实证）：

你本机 Dream 记忆 antigravity-platform.md 的 [MEM-AGY-002] 已经用历史会话日志验证过：面对 model_decision 或主观触发门槛，强主模型几乎 0 触发。原因很直观——强模型看到任务会觉得“这事我直接就能做”，懒得多花一轮 read_file 去查外部 SOP。而 Skill 的自动发现机制，底层跟 model_decision 完全一回事。

  • 本机 <skills> 列表严重拥挤且信噪比失真（刚实测数据）：

此刻注入你这轮对话系统提示词 <skills> 里的条目已经多达 53 条（37 个全局自动发现 + 5 个插件自动发现 + 11 个内置）。而且存在两个真实的“配置债”：

  • 描述严重膨胀：仅全局 39 个 Skill 的 YAML frontmatter 字符数合计就达到 29,398 字符（中位数 735 字符），尤其是 wps-office-suite 单条描述就塞了 2,093 字符的 v5.1–v5.4 更新日志，experimental-design / statistical-power / citation-management / paper-lookup 等都在 1,200 字符上下。模型每轮还没干活，先要在近 3 万字符的技能清单里“大海捞针”。
  • 重复挂载：domain-modeling、grilling、share-conversation 三个 Skill 同时存在于 ~/.gemini/config/skills/ 和插件目录里，此刻在系统提示词里真实出现了两次（grill-me 和 grill-with-docs 也两处重复，只是带了 disable-model-invocation: true 未进自动清单）。
  • 防跑偏类 Skill 存在“元认知悖论”（合理推断，待实测验证）：

工具类 Skill（如“帮我做一个 PPT”）语义信号非常显性，模型容易想起去读 ppt-master；但“防跑偏 / 排错卡死”类 Skill 往往在模型已经陷入错误假设、上下文变长时才需要，此时恰恰是模型最不容易主动跳出来查 <skills> 的时刻。

三、核心架构推演：“不缺额度时，Skill 并入全局记忆/规则 vs 规则抽成 Skill，延续下去会怎样？”

这是你提得最有洞察力的问题。我们先推演两条极端路线延续半年后的真实终局，就能看清为什么“不缺额度”也不能靠单纯的合并或拆分解题。

路线 A：不断把有用的 Skill 合并进全局规则或全局记忆（Always-on 膨胀）

  • 短期体感：爽。因为原本漏触发的流程变成每轮常驻，命中率立刻拉满。
  • 延续下去的 3 个失效机制：
  • 未触上限先中“注意力稀释”：大模型的有效指令遵循能力远小于它的最大上下文窗口。当你把 10 个不同领域的 SOP（写代码、做 PPT、跑统计、画图、发 PR）全塞进 always_on，中段规则会进入静默失效——模型不会报错，只是顺手把中间几条忘掉（你在外部双核交叉复审里也确认了这一核心约束）。
  • 跨场景指令互相打架：写科研论文讨论时被软件工程的“最小 diff / 少写 prose”拽偏，或者简单问答时被迫走繁琐的规划验证仪式，迫使你不停往规则里打“例外补丁”，文本越滚越厚。
  • 触发 Antigravity 硬降级反而退回原点：Antigravity 对 always_on 规则设有单文件 24 KB 截断和总计 20,000 token 硬预算；一旦超标，系统会自动把最大的规则文件从全文注入静默降级为路径指针（- <path>: <description>），兜了一大圈又退化回了“赌模型自觉去读”。
  • 污染记忆的定位：全局记忆（Dream）存的是陈述性事实（你的物理实验背景、本机 Python/FFmpeg 路径、踩过的平台坑）；把程序性 SOP（怎么做某类任务）塞进记忆，会导致每次 /dream 巩固和跨项目检索时事实与流程混在一起，极难维护。

路线 B：把全局规则 / 记忆中的固定片段大量拆成 Skill（过度碎片化）

  • 短期体感：全局规则看起来极度优雅精简。
  • 延续下去的失效机制：
  • 高频底层护栏跌落到概率触发区：一旦把跨任务都需要生效的护栏（例如“先审前提”“双核前置检查点”“同错两次停手”）拆进自动发现 Skill，按照本机 [MEM-AGY-002] 的实测规律，绝大多数回合强模型会直接跳过它，变成“配置里写得头头是道，运行时几乎裸奔”。
  • 你被迫记住几十个 /skill-name 口令：系统变成了手动驾驶，反而增加了你每次发消息前的认知负担。

真正能长期良性演化的结构：四层正交边界（不是二选一）

把“内容性质”和“触发要求”拆开看，答案就非常清楚了：

  • Layer 1：Always-on 全局规则（只留跨任务不变量 + 硬触发路由表）
  • 你目前 3 份全局规则合计才 7,315 B（~7.1 KB），其实非常精瘦健康！
  • 适合放这里：所有任务都成立的高层护栏（core-reasoning-protocol.md）、带客观信号的强路由（deepseek-subagent.md）、以及极紧凑的索引（Dream AGENTS.md）。
  • 不适合放这里：超过 5 行的特定领域 SOP、仅在少数任务出现的长步骤清单。
  • Layer 2：分层记忆（只存“事实与约束”，不存“操作流水线”）
  • 适合放这里：关于你本人、本机环境、课题上下文（CONTEXT_<课题>.md）、已证实的平台/工具坑点。
  • 从全局记忆抽成 Skill 的唯一合理情形：如果你发现某条记忆里长出了一套反复执行的多步脚本/操作手册（比如“从实验数据到出图再到排版的一套固定命令”），那才应该把它从记忆里抽出去做成 Skill，而在记忆里只留一句指针和硬坑点。
  • Layer 3：按需 Skill —— 必须分成“自动瘦身池”和“手动 /命令 池”两档
  • 自动发现池（保持少而精，理想控制在高频 10–15 个以内，每条 description ≤200 字符只写“何时触发”，绝不写更新日志）：留给高频、触发词极明确的场景（如做 PPT、画科研图、去 AI 味、统计分析）。
  • 手动召唤池（显式加 disable-model-invocation: true 或放到冷备目录）：重型、低频或高侵入工作流（类似你本机已有的 grill-me，或者 ds-best-of-n 这种多路并行重活），不占自动 <skills> 清单注意力，想用的时候敲 /skill-name 100% 精准拉起。
  • Layer 4：Lifecycle Hooks（hooks.json）—— 接管“最怕模型偷懒漏做”的硬红线
  • 这是 ds-lessons 思路在 Antigravity 里的终极落地。凡是靠文字规则说了三遍模型还会忘的事（比如改动特定目录代码后没跑测试就想结束回合），用 Stop 或 PreToolUse Hook 做确定性检查，比把文字规则写长 10 倍有效得多。

*(注：我曾考虑过另一种方案——做一个类似 ds-help 的“总路由 Skill”，把其他 50 个 Skill 全藏在它的 references/ 下，只留 1 个总入口给模型。后来放弃了这个方案，因为这会强行增加一轮“先读总目录 → 再读子 Skill”的二次跳转延迟，在高频单步任务里反而更容易被强模型嫌麻烦直接跳过；不如直接瘦身顶层清单 + 区分自动/手动两档。)*

四、要不要根据 deepseek-stack 自制一个 Skill？以及下一步怎么走？

在动手新建之前，我不替你过早拍板，提供 3 条可以自由组合的推进路线（附各自代价）：

  • 路线 1：先给现有技能库做一次“体检减脂”（最推荐作为第 0 步）
  • 做法：① 先跑一段只读统计脚本，查你过去历史对话的 transcript.jsonl，看这 53 个 Skill 里到底哪些被真实 read_file 触发过、哪些至今 0 次（外部可证伪验证，靠数据不靠猜）；② 清理 5 个与插件重复挂载的目录；③ 精简 wps-office-suite 等超长 frontmatter（把 2,000 字更新日志移出 description）；④ 把低频/重型 Skill 标为 disable-model-invocation: true 转为手动 /命令。
  • 收益 / 代价：立刻提升你现有所有好 Skill 的真实自动命中率；代价仅需 10 分钟审核清理清单。
  • 路线 2：微升级全局护栏 + 自制 1–2 个高杠杆专属 Skill（吸收 deepseek-stack 精华）
  • 微升级现有全局规则（不膨胀，总计仅增 ~6 行）：在 core-reasoning-protocol.md 里补两条跨任务通用铁律——① 同一故障连续 2 次修复失败即强制停手验共享前提（ds-unstick 核心）；② 关键结论显式区分 实测 / 推断 / 待验。
  • 自制 1–2 个高价值手动/半自动 Skill（采用 deepseek-stack 的 Steps + Hard Stop When + Rules 紧凑风格，单文件控制在 2 KB 左右）：
  • 候选 A：debug-unstick（或合并成 verify-and-unstick）——专治卡壳排错与高危改动，融合 ds-unstick（前提探针 + 清场换路）+ ds-blast-radius（5 级举证阶梯）+ 联动你的同济双核 code_audit / test_forge。
  • 候选 B：best-of-n（手动 /best-of-n 触发，disable-model-invocation: true）——专为“不缺额度追求极致质量”定制，直接调用 Antigravity 原生 swarm(workspace:"share", n:3) 跑盲评打分 + 局部嫁接。
  • 代价：新增 1–2 个精准技能，几乎不增加自动清单负担。
  • 路线 3：直接实验 1 个确定性 Hook（把 ds-lessons 真正跑起来）
  • 做法：挑 1 个你日常最烦的“模型口头说好了但没实测/漏了某一步”场景，在 ~/.gemini/config/hooks.json 或具体项目 .agents/hooks.json 里写一个轻量 PreToolUse 或 Stop 校验脚本。
  • 代价：需要定义明确的触发条件（避免误拦日常纯聊天回合）。
