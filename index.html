核心判断：你没搞错目标，确实该把“审查”和“翻译”拆开

一句话点明核心矛盾：现有路由器 ai-router.ts 是按单一优先级排队（同济优先 → 单一备用回退），没有按任务含金量分流，导致高推理含量的「语义审查」与低技术含量的「纯外文翻译」共用同济周积分，同时让免费的智谱通道闲置。

回看代码里的 4 类调用，现状一目了然：

  • 高价值审查（ai-focus-curator.ts 精选审校 / 时政 L2 严审）：需要准确判断 keep/noise、1–5 星打分、避免时政水文漏网——这才是同济 DeepSeek-V4.1-Flash 真正该干的活。
  • 纯翻译（目前在白烧同济积分的三处重灾区）：
  • 详情抽屉全文译 translateSingleItem（ai-settings.ts）：单次喂最多 2400 字正文、吐 500 字译文，Token 消耗大、技术含量低，却默认先走同济。
  • 列表批量纯补译 translateBatchForList（ai-settings.ts）：同样没设 skipTongji，默认先走同济。
  • 手动全库外文翻译 backfillAi(mode="english")（ai-admin.ts）：直接走 reviewItems() 且不跳同济。
  • 语义去重（ai-dedup.ts）：此前已经硬隔离，不占同济额度。
一个值得提前对齐的省额度细节：在「高价值审查（reviewItems）」本身里，模型已经把外文标题和摘要读进上下文了，顺带在同一个 JSON 里输出 ≤48 字的 titleZh 和 ≤80 字 takeaway 边际成本极低（只多几十个输出 token），反而省掉一次对免费池的二次 HTTP 往返。真正该硬切去免费渠道的是“纯翻译”：详情抽屉全文翻译（summaryZh）、列表补译、手动外文批量译，以及无需审查只想先看懂的分区外文。

讨论一：任务路由矩阵怎么改最合理？

在严守 CONTEXT_ai_radar.md「AI 零成本红线（绝不强制依赖同济，离校/无 Key 时可优雅降级）」的前提下，建议改为按 purpose 分流：

| 任务类型 | 路由策略 | 理由 |

| :--- | :--- | :--- |

| review（精选审校 / 时政 L2 严审） | 同济优先 → 免费公网池回退 | 把同济周积分和快响应（3~4s/批）集中花在精准去噪、打分和时政 L2 门禁；离校/触顶仍能无缝回退免费池。 |

| translate（详情全文译 / 列表纯补译 / 手动外文译） | 仅走免费公网池（硬跳过同济） | 零消耗同济积分；技术门槛低，7B~9B 免费模型完全足以做到流畅看懂。 |

| dedup（语义去重） | 仅走免费公网池（维持现状） | 保持不占同济额度，直接复用同一套免费池的容灾能力。 |

同时可以顺手解耦预算账本：目前 ai-budget-policy.ts 的日限 120 条把“审查”和“抽屉自动翻译”混扣在一起；纯翻译彻底免费化后，建议让 focusBudget(120/日) 只管审查，纯翻译走独立的宽松上限（或仅受免费池并发/防呆上限约束），不再抢审查配额。

讨论二：智谱一个不够，用“双智谱号”还是“多家免费模型混用分配”？

先说结论：强烈优先「多家异构免费模型池（Free Provider Pool）」，不建议专门为了扩容去搞“双智谱号”；但我们在架构上把池子做成通用的「多槽位列表」，天然同时兼容“异构多厂商”和“填入你已有的第二个合法账号”。

关键推理与方案对比

  • 为什么智谱单号会觉得不够？
  • 并非总额度不够（智谱 Flash 系列长期免费），而是卡在单账号免费层并发上限低（公开资料通常为 1~2 并发）+ 响应偏慢（刚才实测 4 条耗时 9.5s）。多批同时跑或连点几篇外文抽屉，很容易排队堵车或触发 429。
  • 推荐方案：异构多厂商免费池（OpenAI 兼容统一接入）
  • 现有预设 ai-settings.ts 里本来就内置了 3 家国内直连免费渠道，实务上还可以加 1~2 家大厂免费层作为补充（注：以下额度为联网检索到的公开政策，你当前账号的实测 RPM/模型 ID 均属未验证，接入前需实机测试）：
  • 智谱 AI（glm-4-flash / 最新免费 Flash）：长期免费、无日次硬顶，适合低并发兜底（单槽并发设 1~2）。
  • 阿里魔搭 ModelScope（Qwen/Qwen2.5-7B-Instruct 等）：实名后每日约 2000 次免费、按日刷新，中文科技翻译表现很稳（单槽并发设 2）。
  • 硅基流动 SiliconFlow（免费层 7B/8B/9B 开源模型 + 新户赠额度）：国内直连速度快、OpenAI 兼容度高（单槽并发设 2）。
  • 可选大厂补充：腾讯混元 hunyuan-lite（长期免费、长上下文）或百度千帆 ERNIE-Speed（兼容 OpenAI 接口）。
  • 收益：3 家各 1~2 并发就能拼出 4~6 路真实并发，互不共享限流桶，且一家限流/维护时其余槽位照常工作。
  • 考虑过但放弃（或不作主力）的方案与原因：
  • 专门注册两个智谱号轮询（不推荐作主力）：① 同一台电脑、同一出口 IP 高频轮询多号，有触发智谱同源风控/限流甚至连坐封号风险（且国内平台实名/手机号绑定）；② 共享同一故障域，智谱晚高峰变慢或抽风时双号一起慢。如果你本来就有亲友/个人现成的合法第二账号，填进通用池里跑是可以的，但不值得专门为并发去养同厂商小号。
  • 纯传统免费机器翻译（Google/Bing 网页逆向等）：虽然快且不要 Key，但非官方逆向接口极易失效、被限流或强依赖代理（违背国内直连稳定原则），且无法生成 1~2 句大白话 takeaway，AI 专业术语也经常翻得生硬；7B 级免费 LLM 已经足够快且直接复用现有 /chat/completions 协议，零额外维护成本。
  • 本地跑 Ollama 小模型：零网限，但常驻吃内存/显存，与 AIRadar.exe 轻量无窗常驻后台的定位冲突（不过现有 allowNoAuthLocal 已留好口子，以后随时可当池里的一个本地槽）。

池内“分配”怎么设计最稳、不过度设计？

  • 最闲槽优先（按单槽独立并发上限分配）：每个免费槽位各自配置 baseUrl / model / apiKey / maxConcurrency / enabled；派单时选未冷却且 inFlight / maxConcurrency 最小的槽位（天然让快、并发高的渠道多干活，不把智谱压爆）。
  • 单槽独立 429 退避冷却 + 失败换槽：某槽报 429 或 5xx/超时，只冷却该槽（如 60s 指数退避，上限 10 分钟），该次请求立刻换池内另一个健康槽重试（最多换槽 1~2 次，防雪崩放大）。
  • 严守现有安全边界：每个槽位独立校验 apiKeyOrigin、严禁把 agi.tongji.edu.cn 或校内 VIP 填进免费池绕过同济路由与账本；放弃“按质量动态投票/强制 response_format（防小厂商 400）/自动轮换养号”等过度设计，继续沿用当前正则提取 JSON + 严格字段校验。
